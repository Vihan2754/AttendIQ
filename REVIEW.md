# REVIEW.md

List every defect found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` L72–74 | Always returns `{"status":"ok"}` even when MongoDB is down. Contract says "Returns 200 only if MongoDB answers a ping, otherwise 503." | Kill MongoDB, call `GET /health` → still 200. | Added `db.command("ping")` in a try/except; raises `HTTPException(503)` on failure. |
| 2 | `list_employees` L93 | `skip = page * page_size` — for page=1, skips the first 20 records entirely. Should be `(page - 1) * page_size`. | `GET /employees?page=1` returns records 21–40 instead of 1–20. | Changed to `skip = (page - 1) * page_size`. |
| 3 | `list_employees` L94 | `total = db.employees.count_documents({})` ignores the `department` query filter. Contract: "`total` always reflects the applied filters." | `GET /employees?department=Engineering` returns `total` = all employees, not just Engineering ones. | Changed to `db.employees.count_documents(q)` where `q` is the built filter. |
| 4 | `list_employees` L89–95 | No `.sort()` applied. Contract: "Sorted by `emp_code` ascending." | `GET /employees` returns employees in insertion order. | Added `.sort("emp_code", ASCENDING)` to the MongoDB cursor. |
| 5 | `list_attendance` L144–150 | `docs = list(db.attendance_logs.find(q))` loads the **entire** filtered collection into memory, then sorts and slices in Python. Contract: "Must stay fast on a collection of ~100,000 records; do not load the collection into memory." Also sorts by date only — missing secondary sort on `emp_code`. | On 100k records, response time degrades to seconds and memory usage spikes. | Replaced with `.sort([("date", DESCENDING), ("emp_code", ASCENDING)]).skip(skip).limit(page_size)` inside MongoDB; `total` via `count_documents(q)`. |
| 6 | `punch_in` L102 | `datetime.fromtimestamp(body.punched_at / 1000)` returns a **naive local-time** datetime. On a server not running in IST this produces the wrong IST calendar date. `datetime.now()` has the same problem. | Run the app on a UTC server; punch in at 00:15 IST (18:45 UTC previous day) — `date` stored as previous UTC date, not the correct IST date. | Replaced with `epoch_ms_to_dt()` (converts ms → UTC-aware, whole-second truncated) and `now_utc()`. IST date derived via `ist_date_str()` which converts to IST first. |
| 7 | `punch_in` L101 / L113 | `emp = db.employees.find_one(...)` is not checked for `None`. When the employee doesn't exist, `emp["shift_start"]` raises `TypeError: 'NoneType' is not subscriptable` — a 500 crash. Contract: "404 unknown employee." | `POST /attendance/punch-in` with `{"emp_code":"EMP9999"}` → 500 Internal Server Error. | Added `if emp is None: raise HTTPException(404, "employee not found")` immediately after the lookup. |
| 8 | `compute_late_minutes` L33–37 | Sub-second microseconds not removed before computing the delta. R1: "Before any calculation, instants are truncated to whole seconds." Also the shift-start `datetime` is computed in the server's local time zone rather than IST. R2 example: 09:40:01 IST → 10 late min; without IST math this can be off by ±5.5 h. | Punch-in at 09:40:01.500 IST — microseconds cause it to seem > 10 min late; on a UTC server the shift-start is built in UTC, giving a wrong delta. | Rewrote `compute_late_minutes`: accepts a UTC-aware datetime, converts to IST, builds shift-start in IST, computes delta in whole seconds (truncation already handled by `epoch_ms_to_dt`). |
| 9 | `compute_overtime` L44–47 | Mixes a naive `punch_out` (from Bug 6) with an IST-aware `end` datetime → `TypeError: can't subtract offset-naive and offset-aware datetimes`. Also has no threshold check: R3 says overtime counts only when ≥ 30 min. | Any punch-out in the original code would crash here. Separately: punching out 15 min after shift-end would incorrectly return 15 OT minutes. | Rewrote `compute_overtime`: both operands are now aware datetimes (IST); threshold enforced (`return raw if raw >= 30 else 0`). |
| 10 | `create_employee` L82 | `doc["created_at"] = datetime.now()` is naive local time. Contract's `Employee` schema requires `created_at` as **epoch milliseconds** (integer); FastAPI serialises a `datetime` as an ISO string instead. | `POST /employees` → `created_at` in response is `"2026-10-15T10:23:45.123456"` instead of `1760610225000`. | Changed to `now_utc()` (UTC-aware, whole-second); serialised to epoch ms by `serialize_employee()`. |
| 11 | `list_attendance` L148–149 | Raw MongoDB documents returned without conversion. `punch_in` / `punch_out` are BSON datetimes; `history[].at` and nested datetime values inside `changes` are also BSON datetimes. Contract requires all instants as **epoch milliseconds integers**. | `GET /attendance` → `punch_in` is `"2026-07-06T03:58:00"` instead of `1751773080000`. | Added `serialize_attendance()` helper that converts all BSON datetimes → epoch ms, handles nested `history` entries, and defaults missing legacy fields. |
| 12 | Startup (none) | No database indexes created anywhere. Contract: "Create all indexes at startup, idempotently." Without indexes all queries do `COLLSCAN`; the grader checks `IXSCAN` via `/admin/explain`. Concurrent duplicate punch-ins also cannot be made safe without a unique index. | Start the app, insert 100k records, run any analytical query — slow `COLLSCAN`. `/admin/explain` fails the grader. | Added `@app.on_event("startup")` that calls `create_index()` for: unique `emp_code` on employees, compound `(department, emp_code)`, unique `(emp_code, date)` on attendance_logs, compound `(date DESC, emp_code ASC)`, and `(emp_code, date ASC)`. |
| 13 | `EmployeeIn` model L53–60 | No regex validation on `emp_code` (contract: `^EMP\d{4,6}$`), no email pattern check, no `shift_start != shift_end` check, no `HH:MM` format validation, and `page_size` in both list endpoints has no upper-bound cap (contract: max 100). | `POST /employees` with `emp_code: "BADCODE"` → 201 instead of 422. `GET /employees?page_size=9999` returns all records in one page. | Added `@field_validator` decorators for `emp_code` (regex), `shift_start`/`shift_end` (HH:MM), `email` (pattern). Added `@model_validator` for `shift_start != shift_end`. Added `Query(ge=1, le=100)` on `page_size` in both list endpoints. |
| 14 | `punch_in` L104–105 | Check-then-insert (`find_one` → `insert_one`) is not atomic. Two concurrent requests for the same employee+date can both pass the `find_one` check and both succeed with 201, creating duplicate records. Contract: "Concurrency: if the same employee punches in twice … exactly one request gets 201 and the rest get 409." | Use a load tester to send two simultaneous punch-in requests for the same employee+date → two 201 responses, two records in the collection. | Removed the `find_one` guard. The unique index on `(emp_code, date)` ensures only one insert succeeds; the other raises `DuplicateKeyError`, caught and converted to 409. |

## Things examined and decided NOT to be defects

| Item | Reasoning |
|---|---|
| `compute_work_hours` using `round()` (built-in) | Fixed as part of Bug 9 (R4 requires half-up rounding, not Python's banker's rounding). Replaced with `half_up()`. While Python's `round()` does banker's rounding, for the specific case of 2 decimal places on typical work-hour values the difference is rare — but it is still a specification violation. |
| `IST = timezone(timedelta(hours=5, minutes=30))` | Correct definition. Not a bug. |
| `doc.pop("_id", None)` after `insert_one` | Correct — `insert_one` mutates the dict by adding `_id`; popping it before returning is the right approach. Preserved (inside `serialize_attendance` / `serialize_employee`). |
| `Optional[int]` for `punched_at` | Semantically correct (omitting means "use current time"). The missing epoch-ms range validation was Bug 13; the type itself is fine. |
